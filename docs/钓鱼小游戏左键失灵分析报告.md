# 钓鱼小游戏「左键有时候失灵」分析报告

> 分析对象：本项目 CustomFishing（mgtown 分支）
> 分析范围：`右键收线 → 开启小游戏 → 小游戏内按键判定`
> 文档版本：**v2（2026-10-21 更新）** —— v1 为纯诊断，v2 已包含 P0 级修复记录
> 代码状态：`api/.../AbstractGamingPlayer.java`、`core/.../BukkitFishingManager.java` 已修改（+22 / -10）

---

## 一、结论摘要

左键失灵不是一个 bug，而是 **4 个互相独立的输入丢失通道叠加**的结果。它们各自只在特定条件下触发，叠在一起就表现为「有时候好用、有时候没反应」，玩家很难自己找到规律。

| 编号 | 根因 | 触发条件 | 影响面 | 确定性 | 状态 |
| :-- | :-- | :-- | :-- | :-- | :-- |
| **P0-1** | `firstFlag` 主动丢弃第一下左键，且**每次右键后重新武装** | 每局第一下左键；任何一次右键之后的下一 下左键 | 所有左键类小游戏 | 代码必然，100% 复现 | ✅ **已修复** |
| **P0-2** | 输入源只接受 `LEFT_CLICK_AIR` | 准星落在方块上（→ `LEFT_CLICK_BLOCK`）；准星落在 3 格内实体上（→ 攻击实体，无事件） | 所有小游戏 | 取决于视角 | 🟡 **方块分支已修，实体分支未修** |
| **P0-3** | `accurate_click` 类型**根本不消费左键** | 默认配置 46 个游戏里 34 个是这个类型 | 占比 74% 的默认游戏 | 设计如此 | ⬜ 未修（玩法语义，需你决定） |
| **P1-4** | 判定字段跨线程非 `volatile`，且判定时刻与玩家看到的画面错位 | `accurate_click`（每 6~12ms 走一格）+ 网络 RTT 50~150ms | 精度类游戏「点中却判失败」 | 稳定存在 | ⬜ 未修 |
| **P1-5** | 连点计数非原子（`++` / `-=` 跨线程） | `click_v2` 掉进度 | 连点类游戏 | 概率性 | ⬜ 未修 |
| **P1-6** | 结束到钩子销毁之间约 1 tick 的「僵尸窗口」 | 结束瞬间再点 | `dance` 抛 `ArrayIndexOutOfBoundsException` | 概率性 | ✅ **已修复** |
| **P1-7** | 每 tick 在异步线程解析 MiniMessage + 发 Title（最高 150 次/秒/人） | 在线人数多 / CPU 抖动 | 放大以上全部问题 | 环境相关 | ⬜ 未修 |
| **P2-8** | 客户端与平台差异 | 按住不放、超快连点、基岩版、鱼竿不在主手 | 局部 | 条件性 | 🟡 主手判定已放宽 |

**一句话结论**：`firstFlag` 让「每局第一次左键 + 每次右键后的第一次左键」必然被吞；`LEFT_CLICK_AIR` 单通道让「准星压在方块上」的左键彻底收不到。**这两条已在 v2 修复**。剩下最大的体验缺口是 `accurate_click`（74% 的默认游戏）本来就不认左键，以及在「准星压在实体上」时服务端根本收不到左键事件。

## 三、根因详解（含修复后状态）

### 3.1 P0-1 ✅ `firstFlag` 主动吞掉输入

`api/.../game/AbstractGamingPlayer.java`（**v1 原代码**）

```java
public boolean internalLeftClick() {
    if (firstFlag) { firstFlag = false; return false; }   // 丢弃
    return handleLeftClick();
}
public void internalRightClick() {
    firstFlag = true;                                     // 每次右键重新武装
    handleRightClick();
}
```

`internalRightClick()` 的调用点：`onReelIn`（第 291-302 行，右键收线 = 小游戏的正常结束方式）、`onCaughtEntity`（第 259-289 行，右键点实体）。

v1 状态机：

| 时刻 | `firstFlag` | 该次左键 |
| :-- | :-- | :-- |
| 新局创建 | `true` | — |
| 第 1 次左键 | `true → false` | **丢弃** |
| 第 2 次及以后 | `false` | 正常 |
| 任意一次右键 | `false → true` | — |
| 右键之后第 1 次左键 | `true → false` | **丢弃** |

这段代码本意是吞掉「点鱼开局时残留的挥手包」（客户端 ATTACK 与 Swing 是两个包，Swing 晚于 `REEL_IN` 到达），但它**不区分这一局是用左键开的还是右键开的**：用右键收线开局的玩家，被吞掉的是真实的第一下操作。对 `dance_game_easy`（只出左右键，`easy: true`）尤其致命 —— 「右键后紧跟左键」的那些左键 100% 消失，玩家看到的是「按了没反应」，再按一次才生效，节奏全乱。

> 被吞的左键**不会判错**，只是静默消失，所以玩家既看不到失败提示，也看不到进度，只会觉得「卡了一下」。

**v2 修复**：`firstFlag` 已删除，改为 120ms 开局宽限窗口（只挡残留包），并给 `internalLeftClick/RightClick` 补了 `isValid()` 前置判断。详见第二节。

### 3.2 P0-2 🟡 只有「准星对着空气」的左键才算数（方块分支已修）

`BukkitFishingManager.java:171-192`

Bukkit 的左键事件按**准星命中物**分流，三条路径互斥：

| 准星命中 | 客户端发包 | 服务端事件 | v1 是否收到 | v2 是否收到 |
| :-- | :-- | :-- | :-- | :-- |
| 空气 / 水面（水不是方块目标） | `Swing` | `PlayerInteractEvent(LEFT_CLICK_AIR)` | ✅ | ✅ |
| 任意方块（岸边、木栈道、船、脚边地面） | `START_DESTROY_BLOCK` + `Swing` | `LEFT_CLICK_BLOCK` | ❌ 被原第 173 行过滤 | ✅ **已修** |
| 3 格内实体（生物、掉落物、盔甲架、其他玩家等） | `Interact(ATTACK)` | `EntityDamageByEntityEvent`（**不产生** `PlayerInteractEvent`） | ❌ | ❌ **仍未覆盖** |
| 主手为空 / 非鱼竿 | `Swing` | `LEFT_CLICK_AIR` + `material = AIR` | ❌ 被原第 175 行过滤 | 🟡 空手已兜底，非鱼竿仍按设计拒绝 |

第三行是 Bukkit 的公开已知限制（社区标准兜底方案是监听 `PlayerAnimationEvent`）。钓鱼时玩家会不停微调视角看浮标，准星在「水面 / 方块 / 实体」之间来回切，所以失效率看起来是随机的。

### 3.3 P0-3 ⬜ 74% 的默认小游戏本来就不认左键

`registerAccurateClickGame()`（`BukkitGameManager.java:920-998`）**没有覆写 `handleLeftClick()`**，走基类实现 `return false`（`AbstractGamingPlayer.java:146-148`），只在 `handleRightClick()` 或超时时结算。

默认 `contents/minigame/default.yml` 共 46 个游戏：`accurate_click` 34、`click` 3、`dance` 3、`hold` 3、`tension` 3。3 个 `click` 还显式写了 `left-click: false`（第 1622/1630/1638 行），其 `handleLeftClick()` 只是 `return true` 取消事件、不计数（第 512-517 行）。

**默认配置下真正消费左键的只有 `dance`（3 个）。** 玩家在 34 个精度类游戏里狂点左键，本质上是无效操作，也会被记成「左键失灵」。

### 3.4 P1-4 ⬜ 判定与画面错位 + 跨线程数据竞争

```java
// AbstractGamingPlayer.java:76-78   推进任务跑在 ForkJoinPool(16)，非主线程
// AbstractJavaScheduler.java:73-76  scheduleAtFixedRate → worker.execute
// BukkitGameManager.java:958-962    accurate_click：6~12ms/格（≈150 次/秒）
```

`progress` / `currentIndex` / `clickedTimes` / `hold_time` 都是普通字段，工作线程写、主线程读：

- 无 `volatile` / 无同步 / 无原子类 → 主线程可能读到旧值；
- 服务端判定用的是「点击包到达那一刻的 progress」，玩家看到的是「客户端最近一次渲染的 title」，相差 **网络单程 RTT + 1~2 个渲染帧**。指针 12ms 走一格时，80ms 延迟 ≈ 6~7 格偏差。

这不是随机，而是**系统性相位差**，玩家只能靠提前量弥补，体感就是「判定很飘」。

### 3.5 P1-5 ⬜ 计数丢失

```java
// click_v2（BukkitGameManager.java:576-611）
this.clickedTimes -= (baseDecreaseRate + extraDecreaseRate * gameSetting.difficulty());  // 工作线程
clickedTimes++;                                                                        // 主线程
```
非原子读改写 → 掉进度，表现为「点了但进度没涨」。

### 3.6 P1-6 ✅ 结束窗口与异常

```java
// AbstractGamingPlayer.java:228-240
destroy();                    // valid=false，但 hook.gamingPlayer 仍指向该对象
scheduler.sync().run(...);    // 下一 tick 才 hook.destroy()
```

1 tick 内 `getGamingPlayer()` 仍 `isPresent()`，点击继续进入 `handleLeftClick()`；`dance` 的 `order[clickedTimes]` 无边界检查 → `ArrayIndexOutOfBoundsException`，点击静默消失并刷一条 `Could not pass event PlayerInteractEvent to CustomFishing`。

**v2 修复**：`internalLeftClick/internalRightClick` 前置 `isValid()` 判断，直接挡死这条路径（未改动 `dance` 本身）。

### 3.7 P1-7 ⬜ 每 tick 发 Title 拖慢主线程

`showUI()`（如 `BukkitGameManager.java:987-993`）每 tick 都做一遍「MiniMessage 解析 → JSON 序列化 → 发包」，`accurate_click` 下等于 **150 次/秒/人**，且全部跑在 `ForkJoinPool`。在线人多时：title 抖动/跳格（玩家看到的指针本身就不准）+ 主线程 tick 变长（点击包在队列里堆积）。这会放大前 4 条。

### 3.8 P2-8 🟡 客户端与平台侧

| 现象 | 原因 | v2 |
| :-- | :-- | :-- |
| 按住左键不出来连续点击 | 客户端只在「按下」时发一次挥手包，必须抬起再按 | 服务端无法修 |
| 极快连点丢包 | 挥手动画播放期间的重复点击可能被客户端合并/节流 | 同上 |
| 基岩版（Geyser/Floodgate）失灵更多 | 触摸「点一下」与 Java 挥手语义不同，Geyser 对攻击/交互动有合并与频率限制 | 未处理 |
| 鱼竿不在主手 | 原第 177 行直接 `return`（设计如此） | 空手已兜底，非鱼竿仍拒绝 |
| 鱼竿耐久耗尽 / 游戏中切换物品 | `onItemHeldChange` 会销毁钩子 → 游戏中断 | 未处理 |

## 四、已排除的可能（不必浪费时间排查）

| 假设 | 排除依据 |
| :-- | :-- |
| 被别的插件取消导致收不到 | 监听器是 `ignoreCancelled = false`，事件被取消也能收到 |
| 同一 tick 内多次点击被合并 | 每次点击是独立数据包，逐个派发，不会合并 |
| 权限/条件不满足 | 那会直接开不了局，不是「局内失灵」 |
| 网络丢包 | 丢包会同时影响右键收线，不会只丢左键 |
| 事件优先级被抢 | Bukkit 没有「吃掉事件」的机制，`setCancelled` 不影响本监听器 |

## 六、未修复项与后续（按性价比）

1. **`accurate_click` 接纳左键结算** —— 覆盖 74% 的默认游戏，改动约 5 行，但属玩法语义变更，需先定方案。
2. **准星命中实体时兜底** —— 新增 `EntityDamageByEntityEvent` 监听（`DamageCause.ENTITY_ATTACK` + `damager instanceof Player`），并顺带拦住对小游戏无关实体的伤害。注意不要用 `PlayerAnimationEvent`：它在持续挖掘方块时会持续触发，等于给连点游戏开后门。
3. **判定归位** —— 推进任务改回主线程，或把状态改为 `AtomicInteger`/`volatile` + 主线程快照，并让「判定用的进度」与「最后发给客户端的进度」对齐。
4. **降包频** —— title 只在数值变化时发（或每 2~3 tick 合并），MiniMessage 预编译缓存，把 150 次/秒降到 10~20 次/秒。
5. **`click_v2` 计数原子化** —— `AtomicInteger` + 主线程单调递增。
